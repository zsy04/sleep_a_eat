# Agent 知识体系

> 整理时间：2026-08-16 · mswyl
> 结构：认知 → 构造 → 工程化 → 扩展 → 实践，五层

---

## 总纲（一句话 + 一个公式）

> **Agent = 大模型 + Harness**；Harness 决定模型被用得好不好。
> **任务表现 = 模型上限（训练决定） × Harness 综合利用率（工程决定）**

- Harness 综合利用率 = **核心层（上下文工程，模型可感知）** + **外围层（工具执行可靠性、沙箱、调度，模型不可感知）**
- 上限是天花板，harness 决定能榨出多少；上下文工程是 harness 里最大的一块，但不是全部

# 第一层 · 认知层：Agent 是什么

## 1.1 与软件的关系
- **本质相同，表现与处理方式不同**：Agent 与软件都是处理数据、产生输出。
- **可见性差异**：软件从数据库读数据→处理→输出，**可见性好**；Agent 是**黑盒**，可见性差 → 所以需要可观测性（见 3.4）。

## 1.2 定义：Agent = LLM + Harness
- **Harness 定义**：以「帮助大模型更好地完成任务」为目的而集成的**外围组件系统**——工具、Skill、Agent Loop、记忆、上下文管理、可靠性等。
- **判断标准是"目的"**（是否在帮大模型完成任务），**不是手段**（碰不碰上下文）。
- 举例：Agent 自己算 1+1 可能得 3 或 4（上下文干扰）；通过工具（计算器）把结果固定为 2——工具把不可靠的推理外包给确定性系统。

## 1.3 任务分型
1. **自动化任务**：要**确定性**——结果必须对 → 多依赖工具接管、校验
2. **延伸性 / 预测性 / 推测性任务**：接收数据、注入数据、分析数据 → 要**推理深度** → 需要长上下文、思考空间
3. **单纯分析数据、简化工作**：输入数据 → 模型判断 → 进入不同分支

## 1.4 核心论断：上下文是核心
- 做 Agent 本质 = **动上下文**：工具信息、Skill、记忆都得经过上下文才能被模型"看见"。
- **「上下文是核心」的正确含义**：在 harness 全部组件里，上下文是**模型可感知的核心**；沙箱、调度、Checkpoint 是**模型不可感知的外围执行层**——它们同样是 harness，但不占上下文。
- 两种架构路线：
  - **以 Loop 为中心**（Claude Code / Codex）：往 Loop 里加工具、Skill、知识库
  - **以 ctx 为中心**（DeepSeek harness）：围绕上下文去更改，一切皆插件，可随意组合/拓展/更改
- 大模型的**训练倾向**：喂什么数据就偏向什么（拿代码喂 → 编码强）；这是**倾向**，不是能力上限锁死。

# 第二层 · 构造层：Agent 内部组成

## 2.1 上下文工程（核心）
- **上下文工程 = 设计**：如何结构化地让模型理解要完成什么：
  - 上下文**压缩**（减少 KV 占用 → 省算力和延迟）
  - **KV Cache** 理解（前缀缓存、成本账）
  - **结构化、可读**（首尾效应 / lost in the middle：模型关注最前和最后的内容）
  - **持续性**：之前输入输出的内容，到后面不会发生很大改变（= 可靠性的定义，见 3.1）

## 2.2 记忆系统
- 用人的记忆类比三层：
| 层级 | 类比 | 落地 |
|------|------|------|
| 短期（工作记忆） | 手头正在做的事 | 会话上下文窗口 |
| 会话 / 长期 | 这一长段时间做的事 | 记忆文件（用户画像）+ 向量库/RAG |
| 更长期 | 这一生发生的事 | 可检索的长期记忆 |

- **用户画像文件**：SOUL.md / USER.md / IDENTITY.md——**静态长期记忆**，每次会话固定注入，讲**稳定**；**动态长期记忆**（向量库/RAG，检索进来）讲**覆盖**——多数 Agent 的短板在后者：只有画像，没有真正可检索的记忆。
- 记忆系统三个关键决策：**写入策略**（什么时候写）、**读取策略**（什么时候检索）、**遗忘策略**（什么时候丢）。

## 2.3 工具（手脚）
- **工具 = Agent 能做什么事情的延伸** = 手脚；决定 Agent 的**能力边界**（上下文决定认知边界，工具决定物理边界）。
- 三个层次（协议 → 能力 → 流程，不是并列）：
  - **MCP**：标准化协议（"USB-C 接口"）——读取更多数据，接入任意服务商（高德、数据库…）
  - **Tool**：原子能力（读文件、调计算器）
  - **Skill**：流程封装（把一串 Tool 打包成可复用工作流，例：检索报纸→剪新闻）
- **Tool Schema 设计**：
  - 描述**简短、清楚**；写"什么时候该用"，不写"怎么用"
  - **数量权衡**：工具越多 → 上下文占用越多 → 解法：**工具按需加载（Tool Search）+ Skill 渐进式披露**（不全部塞进上下文，先搜到再加载；描述要准确才能被正确发现）
  - **幂等性**（重试安全）、**使用边界**、**输出 JSON 格式**设计
- 顺序：先解决上下文（想清楚）→ 再挂工具（做得到）。

# 第三层 · 工程化层：从能跑到能用

> 工程化 = 可靠 + 安全 + 成本可控 + 可评估 + 可量化——把「能跑的应用」变成「让人能用的应用」。
> 对照软件工程：能跑 = 功能需求；能用 = 非功能需求（安全/性能/成本/可观测/可维护）。

## 3.1 可靠性 / 可移植性 / 可观测性（三概念拆分）
| 概念 | 问的问题 | 手段 |
|------|---------|------|
| **可靠性** | 输出稳定、可复现、可解析吗？ | 低 temperature、结构化输出 + Schema 校验、校验重试、幂等 |
| **可移植性** | 换环境/换人还能用吗？ | 依赖声明、配置外置、结构化输入输出 |
| **可观测性** | 执行到哪一步看得见吗？ | Trace / 日志 / 状态汇报 |

- 可靠性的本质：LLM 是**概率引擎**，要用**确定性的基础设施包住非确定性的模型**——把概率压到接近确定。
- 三个概念互为依赖：没有可观测 → 不知道哪里不可靠；没有评估 → 不知道可靠是 90% 还是 60%。

## 3.2 安全
- **Prompt 注入**：上下文内容注入导致任务无法完成。
  - **直接注入** vs **间接注入**（通过网页、图片、PDF 等载体）
  - **供应链注入**：工具包投毒（ClawHub 投毒事件）；Claude Code 地区歧视问题
- **核心原则**：把「不可信数据」和「指令」**物理隔离**——数据只进数据区，绝不允许进指令区；防御靠结构隔离 + 输出校验，不靠模型自觉。
- 应对手段：**设定权限（最小权限）、沙箱、危险操作人工审批（human-in-the-loop）、记录日志（审计）**。

## 3.3 成本控制
- Agent 用模型必然花钱：**成本 = 单价 × 次数 × 长度**，四个变量各有打法：
  1. **前缀缓存 / KV 缓存复用**（省"重复计算"）
  2. **模型路由**（简单任务走便宜模型，省"单价"）
  3. **结果缓存**（相同查询不重复调用，省"次数"）
  4. **上下文预算 / 剪枝**（超限压缩截断，省"长度"）
  5. **批处理**（能合并的请求合并，省"次数"）
- **前缀缓存的坑（缓存会悄悄失效）**：动态增删工具、改 Tool Schema、改 system prompt → 整段前缀缓存失效，每轮重新算，账单悄悄变贵且不易察觉。
  - **对策**：前缀缓存设计"稳定优先"——固定内容（系统提示/工具定义/画像）放前缀且尽量不变，动态内容（用户输入、检索结果、摘要指令）放后缀。
  - **实战实证**：上下文压缩（compaction）把**摘要指令作为最后一条 user message**（而非 system prompt）→ 辅助调用 = 真实请求的前缀 → 前缀缓存复用，只算新增指令。
  - **反面案例**：用插件**动态拼装** system prompt（可插拔）换可定制性，代价就是缓存易失效、token 更多。

## 3.4 可观测与调试
- 目标：Agent 能**稳定**地在大量情况下完成任务（例：LangSmith）。
- **可观测性三支柱**：日志（Logs）+ 指标（Metrics）+ 追踪（Traces）；Agent 再加第四根柱子：**决策轨迹**（为什么选这个工具、为什么重试）。
- Trace / Span 记录：每一步 **token 用量**、**工具调用**的操作/返回值/**耗时**、每个模型**输入/输出的内容**、**失败/重试链路**（在哪里失败、重试几次、最后怎么完成）。
- 金句：「改 Prompt 是猜，读 trace 是查」。

## 3.5 评估（多维并列体系）
**评测是多个并列评价面的统一体，不是单一指标、不是包含关系**：
> 完成任务的能力（忠实性/召回率/准确性）、性价比（token 消耗/成本）、可靠性、可观测性、可移植性、长上下文稳定性……共同构成对 Agent 的整体评价。

- **评价维度是并列的**（评测时）；**检索层/生成层只在"失败定位/调试"时使用**（诊断工具，不是评价维度）：
  - 检索层 = **召回率**（相关文档有没有捞全；捞不到 → 必错）
  - 生成层 = **忠实性**（捞到了，模型是否忠于检索内容、不编造）
- **方法与偏差**：
  - 离线评估（golden dataset + 人工打分）、在线反馈、LLM-as-judge（对抗评测）
  - **LLM-judge 三个已知偏差**：自我偏好（不能用同一个模型/工具）、谄媚（sycophancy/肯定感）、位置与长度偏差
  - 对策：降 temperature（缓解随机性）+ **裁判与被测模型异构、盲评、多次采样**（治系统性偏差）
- **评测集（Golden Dataset）**：类似"个税 vs 企业税"的**边界题**最有价值。
- 长上下文稳定性：上下文越长 → 错误率上升（长上下文幻觉）也要评估。

## 3.6 失败兜底（实战四件套）
> 完整链路：**状态机 → Checkpoint → 降级 → 人工**

1. **状态机**（State Machine）：管理流程状态
2. **Checkpoint 埋点**：锁定错误位置（挂起/恢复的基础）
3. **降级策略**（Degradation）：主路径失败 → 次优路径（例：子 Agent 调用失败 → 降级为工具调用兜底）
4. **人工兜底**：最终兜底

# 第四层 · 扩展层：多 Agent（慎用）

- **用途**：① 完成**并行任务**、执行更快；② **专长分工**——不同 Agent 配不同 Skill/工具（A 配文档工具 → 适合出文档；B 配编码工具 → 适合编码）。
- **结构**：主从 / 父子——父 Agent 负责**整体规划**，把任务分给子 Agent。
- **反主流观点**：多 Agent **并不一定更强**——不是越多越强。
- **多 Agent 的问题**：
  - **上下文截断**：父 Agent 给子 Agent 的只能是**摘要浓缩**，不是完整上下文 → 出现与原本要求不符的状况
  - **Token 翻倍**：多 Agent 消耗一定大于单 Agent
  - **协调复杂度**：拆任务、汇总、处理子 Agent 失败，这层本身会出错、会花钱
- **使用三条件（全部满足才上）**：
  1. 任务**天然可以并行**
  2. **信息量大**，难以通过单 Agent 上下文写入
  3. **任务价值足够高**——价值要**覆盖甚至大于**多 Agent 的成本
- **默认单 Agent，多 Agent 是被迫的选择，不是主动的炫技**；质量问题时最常见的错误反应就是"再加一个 Agent"。

# 第五层 · 实践层：如何做

> 定位：前四层讲"是什么、有什么、怎么做好、要不要加"，这一层回答**"怎么学、怎么练"**——把前四层转化为可执行的学习与实践路线。

## 5.1 学习路线：按层递进

| 阶段 | 学什么 | 怎么练 |
|------|--------|--------|
| **① 认知层** | 建立心智模型：Agent = LLM + Harness、表现 = 上限 × 利用率、上下文核心论 | 能用自己的话讲清楚 1.1~1.4，能举出反例（如"不碰上下文也算 harness"） |
| **② 构造层** | 上下文工程、记忆、工具的内部结构 | 实际用一款 Agent，观察它：看 trace、看工具调用记录、看上下文怎么被组装；用几行代码调 LLM API 复现最小 Agent，理解 2.1~2.3 |
| **③ 工程化层** | 可靠 / 安全 / 成本 / 可观测 / 评估 / 兜底 | 逐项动手实践（见 5.2 检查单），每项配一个动作 + 验收标准 |
| **④ 扩展层** | 多 Agent 的三条件与代价 | 先默认单 Agent 做完一个真实任务；遇到瓶颈时再判断是否值得上多 Agent，并用三条件验证 |

## 5.2 工程化层的实践检查单（对应第三层）

> 原则：每条理论配一个**动手动作** + 一个**验收标准**。没有验收标准的练习不算练习。

| 理论 | 动手做什么 | 验收标准 |
|------|-----------|---------|
| **3.1 可靠性** | 给 Agent 输出加结构化 Schema + 校验；同一输入跑 10 次 | 输出格式 100% 可解析；内容漂移可度量 |
| **3.2 安全** | 工具挂最小权限 + 沙箱执行；加审计日志；**主动做一次注入测试**（用恶意网页/文档喂给 Agent） | 注入内容无法篡改指令区；危险操作被拦截或需人工确认 |
| **3.3 成本** | 搭前缀缓存；记录每轮 token 用量；监控缓存命中率 | 能说出"哪些 token 在反复花钱"；动态内容已移出前缀 |
| **3.4 可观测** | 接 trace；记录工具调用/耗时/失败重试 | 出问题时能在 trace 里定位"哪一步、为什么失败" |
| **3.5 评估** | 建 golden dataset（**含边界题**，如易混淆的两类概念）；离线跑分 + LLM-judge 交叉评 | 有基线分数；改一版能对比"变好还是变坏" |
| **3.6 兜底** | 实现状态机 + Checkpoint；**人为制造失败**（断网、工具报错、模型拒答） | 失败后能降级或恢复，不整个任务死掉 |

## 5.3 进一步学习的方向

- **持续输入**：跟踪模型层（新模型能力边界）、协议层（MCP / Skills 标准演进）、框架层（新框架、Agent Runtime）。
- **深挖底层**：选一个自己最在意的点（如上下文工程 / 缓存 / 安全边界），读源码、写笔记、做复现——把"知道"变成"能讲原理"。
- **交叉验证**：用第三层的方法（评估、可观测）给自己的练习项目打分，形成"实践 → 度量 → 改进"的闭环。
